# 閲覧性能の測定設計（M1）

起動直後の1ページだけでは、長い文書の読みやすさを判断できない。固定済みの D10（100ページのデジタルPDF、50ページの画像PDF）を先頭から末尾まで3回スクロールし、描画待ち、GUIイベント処理の遅延、メモリの推移を記録する。

測定用の実行ファイルは本製品と同じ `tatsu_ui` を使う独立ターゲットとする。配布アプリには測定用の操作やボタンを追加しない。Windows上のQt offscreenで実PDFWidgetを描画し、各スクロール地点で表示ページの描画完了を待ってviewportを取得する。3回とも新しい別プロセスから開始し、OSのファイルキャッシュは消去しない。

各移動はviewport高さの75%とし、位置変更から表示ページの描画完了までを計測する。16msのQtタイマーの実際の間隔も記録する。ただし、これは実ディスプレイのFPS、マウス入力から表示までの遅延、コールド起動の測定ではない。待機後の画面取得を含むため、ユーザーが高速にホイールを回した場合の未完了描画とは区別する。

各周回の後に1秒待機し、別プロセスから10ms間隔でRSSとprivate memoryを採取する。先頭・途中・末尾の代表画像、訪問したページ、各移動の生データを残す。メモリが周回ごとに増える場合は、画像・文字・プレビューのキャッシュと文書状態を分けて調べる。

測定プロセスと採取プロセスを共通のOS時刻で照合し、各周回の待機終了250ms前のメモリを使う。終了後の解放を周回末メモリと取り違えない。viewport取得を描画完了時間に含め、その後の証拠PNG保存は含めない。GUIタイマーの間隔には証拠画像の保存等の測定側負荷も含まれるため、製品の純粋な入力遅延の値には転用しない。OSキャッシュと利用者の他作業負荷は統制しない。

検証用の出口は、全ページを実際に表示し、描画待ちがタイムアウトせず、文書内容・dirty・Undo状態・原本ハッシュが変わらず、既存の文字キャッシュとプレビューキャッシュの上限を守ること。新しい性能合格値を後付けしてACCEPTANCEの条件を変更しない。応答時間とメモリは測定値として報告し、Acrobatより速いという主張は同条件の比較を実行するまで保留する。

2026-10-06の改善検証では、独自の連続レイアウトで無効になっていた隣接ページの先読みを補う。表示中のページが準備できてから移動方向の1ページだけを非同期で要求し、表示範囲と前後1ページ以外のコンパイル済みページを解放する。256MiBの既存コンパイルキャッシュ上限は縮小せず、大きなページを新たに拒否しない。先読みは短い待機後に行い、連続移動中は表示ページを優先する。上流の非exportクラスは同じDLL内からだけ扱う最小アダプターをCMakeで追加し、サブモジュールの固定ソースは改変しない。

ページ一覧は本文と注釈のために同じページを二度処理せず、1回コンパイルした本文と既存注釈を縮小画像に描く。OCR、印刷、保存の描画経路は変えない。既存の独立描画との画像一致、遠いページへの連続移動・戻り、文書と履歴の不変を試験し、変更前後のD10を同じ測定手順で比較する。数値が悪化する変更は採用理由と分けて記録する。
